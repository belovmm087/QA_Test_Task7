# Краткие заметки по REST API

## Что такое REST

REST (Representational State Transfer) — это архитектурный стиль построения веб-сервисов.

Основная идея заключается в том, что каждый ресурс имеет собственный URL, а операции над ресурсами выполняются через HTTP-методы.

Пример ресурса:

/api/v2/orders

Пример конкретного заказа:

/api/v2/orders/{id}

---

## Основные HTTP-методы

### GET

Используется для получения данных.

Примеры:

GET /api/v2/orders

GET /api/v2/orders/{id}

Ожидаемый статус:

200 OK

---

### POST

Используется для создания нового ресурса.

Пример:

POST /api/v2/orders

Ожидаемый статус:

201 Created

---

### PUT

Используется для полного обновления существующего ресурса.

Пример:

PUT /api/v2/orders/{id}

Ожидаемые статусы:

200 OK

или

204 No Content

---

### DELETE

Используется для удаления ресурса.

Пример:

DELETE /api/v2/orders/{id}

Ожидаемый статус:

204 No Content

---

### HEAD

Используется для проверки существования ресурса без получения тела ответа.

Пример:

HEAD /api/v2/orders/{id}

Ожидаемый статус:

204 No Content

---

## Важные статус-коды

### 200 OK

Запрос успешно выполнен.

### 201 Created

Ресурс успешно создан.

### 204 No Content

Операция выполнена успешно без возврата данных.

### 400 Bad Request

Ошибка валидации или неверный формат данных.

### 401 Unauthorized

Пользователь не авторизован.

### 403 Forbidden

Недостаточно прав для выполнения операции.

### 404 Not Found

Ресурс не найден.

### 410 Gone

Ресурс ранее существовал, но был удалён.

### 500 Internal Server Error

Внутренняя ошибка сервера.

---

## Что важно для QA

При тестировании REST API необходимо проверять:

- корректность HTTP-методов;
- корректность статус-кодов;
- структуру JSON-ответов;
- обработку ошибок;
- права доступа;
- валидацию входных данных;
- работу с несуществующими ресурсами;
- стабильность сервиса при технических сбоях.

## Что сказать на созвоне

При составлении чек-листа основной акцент был сделан не только на happy path сценариях, но и на проверке контрактов API. Для каждого метода были определены ожидаемые HTTP-статусы при успешном выполнении, ошибках валидации, отсутствии доступа, работе с несуществующими ресурсами и внутренних ошибках сервиса. Дополнительно были включены проверки идемпотентности, структуры ответов и единообразия обработки ошибок.
